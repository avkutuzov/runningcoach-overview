# Синхронизация с intervals.icu

## Что даёт интеграция

[intervals.icu](https://intervals.icu) — бесплатный агрегатор тренировок
с часами Garmin, COROS, Suunto, Polar, Wahoo и календарём. RunningCoach
использует его как источник факта и адресат плана:

- **Синк активностей**: темп, пульс, каденс, TSS, ккал, круги → БД.
- **Синк wellness**: сон, HRV, пульс покоя, вес, шаги.
- **Выгрузка плана**: события в календаре атлета — этапы разъезжаются
  на часы с таргетами пульса/темпа.
- **OAuth**: вход через ICU без ручного ввода ID (см. [pwa](pwa.md)).

Поддержка этапов на часах — через ICU: Garmin/COROS/Suunto/Wahoo/Zwift —
автоматически, Polar — частично, Samsung/Huawei — этапы видны в приложении
ICU. Бот создаёт тренировку в ICU, а раздачу на устройства делает ICU.

## Синк (`scripts/sync_athlete.py`, `intervals_icu/client.py`)

- Синк выполняется по расписанию и «быстрым синком» перед карточками,
  `/progress` и разборами (2–3 дня назад, без попапа пользователю).
- **Guard гостей**: гостевые аккаунты (без ICU) имеют ID с префиксом `g`
  и пропускаются — попытка синка несвязанного атлета не случится никогда.
- **Перенос данных при пере-привязке**: гость → ICU или смена ICU-аккаунта —
  все данные атлета переносятся на новый athlete ID по всем таблицам;
  занятость ICU-id проверяется заранее.

## Выгрузка плана (`plan_push.py`)

Самый хитрый модуль интеграции — конвертация плана недели в события
календаря:

- **События называются `[ПН] ...`** — метка дня в имени. Чистка прошлых
  выгрузок идёт по префиксу `[ПН]/[ВТ]/...`: пересоздание недели не
  оставляет мусора, а события не-планового происхождения не трогаются.
- **Прошедшее не трогается**: дни недели до «сегодня» не удаляются и
  не пересоздаются (история атлета неприкосновенна); «сегодня» создаётся,
  если пробежки ещё нет.
- **Заморозка истории с дыркой для extras**: после выполненной пробежки
  все сегодняшние события считаются историей — НО extras (растяжка/силовая)
  атлет делает вечером ПОСЛЕ пробежки. Поэтому если DSL extras изменился,
  событие находится по имени, DSL сравнивается, при расхождении — старое
  удаляется, новое создаётся.

## DSL `icu_workout` и инвариант сумм

DSL — текстовый формат этапов, который ICU превращает в структуру на часах
(шаги с длительностью/дистанцией и таргетами зоны/темпа). Жёсткий
инвариант: **сумма дистанционных шагов DSL = `distance_km` дня** — иначе
название события («Long Run 15 км») не совпадёт с тем, что реально
прокрутится на часах.

Согласователь `reconcile_day_distances` различает два класса расхождений:

1. `distance_km` описывала **только основной этап** («бег 8 км» при
   разминке 1.5 + 8 + заминке 1.5 = 11 в DSL) → `distance_km := сумма
   всех шагов` (название события должно показывать полный день).
2. DSL ошибся **арифметикой** (этапы 14 при заголовке 15) → правится
   самый большой шаг DSL под заголовок; рабочие отрезки по рецепту
   `main_set` (`6x800`) защищены от самовольного растяжения.

Порядок операций важен: **санитайзер до согласования** — `500m` → `500mtr`
меняет сумму шагов, поэтому reconcile обязан видеть каноничный DSL
(кириллическое «40 м» парсером дистанцией не читается). У легких/длительных
дней основной шаг обязан иметь пульсовую зону (`ensure_main_hr_targets`);
у качественных зону выбирает модель.

Упрощённая логика — в [`examples/plan_dsl.py`](../../examples/plan_dsl.py).

## Итог

Инвариант сформулирован и проверяется **кодом**, а не обещанием модели в
промпте: конвертация «план → календарь → часы» не может разойтись с
названием события. Это самый показательный пример философии проекта:
«конвенция в промпте» — первая линия, гарант в коде — вторая и решающая.
