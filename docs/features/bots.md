# Боты: Telegram и VK

## Что умеют

Два бота с **паритетом фич**: одинаковые команды, reply-меню, FSM-диалоги
и формат вывода в обоих мессенджерах. Атлет может общаться утром в Telegram,
а вечером в VK — увидит тот же план и получит тот же разбор.

### Команды

`/start`, `/plan`, `/adjust`, `/analyze`, `/nutrition`, `/stats`, `/feedback`,
`/report` (боль), `/weather`, `/goal`, `/profile`, `/chat`, `/test`
(тест макс. пульса → прогнозы по Ригелю + зоны), `/assessment`,
`/link` (привязка ICU), `/settings`, `/done`.

### Регистрация — дружелюбный вход

`/start` → главная кнопка **«🔑 Войти через intervals.icu»**: открывается
мини-приложение (Telegram `web_app` / VK `open_app`) → OAuth ICU → аккаунт
связан, ID вводить не нужно; страница закрывается сама, бот в чате
спрашивает «⌚ Привязать часы?». Запасные пути: **гость** (план по анкете,
привязка ICU позже — данные переносятся на новый ID автоматически) и
привязка существующего athlete ID.

## FSM-диалоги

- Онбординг: 6 вопросов (объём, результат, макс. пульс, травмы, время,
  цель) → план по анкете.
- Отзыв о тренировке: 6 шагов + вопросы об условиях → в контекст следующего
  плана.
- Боль: уровень боли КПС/колено + симптомы → учитывается планировщиком.
- Цели, пересчёт плана, чат тренера, предпочтения питания, локация погоды,
  тест макс. пульса.

FSM ботов живёт в памяти — перезапуск сбрасывает незавершённые диалоги,
но все записанные данные уже в БД.

## Утренний разбор тренировки

Самый используемый пайплайн (см. `scripts/worker.py: run_morning_greeting`):

1. Планировщик ставит задачу в **индивидуальное** время атлета
   (`review_time_utc`).
2. Воркер синхронизирует данные из ICU (2 дня назад) — `notify=False`,
   чтобы попап «данные синхронизированы» не приходил перед советом.
3. План на сегодня берётся запросом **текущего** плана — недели, которая
   накрывает сегодня (не «последнего активного»: при двух планах — текущая
   и следующая неделя — тот запрос может вернуть прошлую).
4. Вчерашняя тренировка сравнивается с целью **по дате**: дата активности
   сопоставляется с `week_start_date + offset` дня плана. Названия событий
   с метками дней в ICU могут быть ошибочными — им доверять нельзя,
   поэтому только дата.
5. AI-разбор план/факт по кругам, погода, состояние → живой совет.
6. В конце — **детерминированный** блок «ТОЧНЫЙ ПЛАН НА СЕГОДНЯ»: DSL-этапы
   как на часах, без пересказа AI.

Интересная деталь: повторный экспресс-анализ делается с нуля — из контекста
модели вычищаются старые вердикты (`status/actual/analysis`), иначе модель
«якорится» на прошлом выводе вместо свежих кругов.

## Доставка во все каналы

`scripts/worker.py: send_to_athlete` — контракт проекта: задача ставится
на одну платформу, но результат обязан приходить **во все** чаты атлета
(TG + VK, плюс лента PWA). Тупиковая ошибка «результат придёт в этот чат»
иначе не выполняется никогда:

```python
def send_to_athlete(job, text, keyboard=None):
    for platform, chat_id in _athlete_channels(job['athlete_id']):
        send_to_job({**job, 'platform': platform, 'telegram_id': chat_id}, ...)
```

## Дедупликация задач

Планировщик (`scripts/scheduler.py`) дедуплицирует: одна задача
`morning_greeting` на атлета в сутки (не по одной на платформу) — рассылку
делает `send_to_athlete`. Дайджест тренера с подключенным ICU ставится
в тот же слот утра по той же схеме.

## Инженерные решения

- **VK-клавиатуры** (`vk_bot/keyboards.py`): VK режет inline-клавиатуры
  до 10 кнопок — клавиатуры собираются отдельно, конвертация TG→VK
  ограничивает размер.
- **Лиды**: outer-middleware фиксирует всех пишущих ботам (first/last_seen,
  счётчик, тексты) — полная воронка без ручного учёта.
- **Ответ AI-текста унифицирован**: HTML от модели конвертируется в
  VK-совместимый текст (`vk_bot/format.py: html_to_vk_text`), клавиатуры
  — тоже конвертируются.
- **API-контракт reply-кнопок**: смена текста кнопки = смена хендлера в
  одном коммите — «магические строки» фиксируются как контракт.
