# Архитектура RunningCoach

## Общая схема

```
                        ┌────────────────────────────────────┐
                        │           PostgreSQL 16            │
intervals.icu API ◄─────┤  атлеты, планы, факты, зоны,       │
        ▲               │  wellness, очередь job_queue,      │
        │               │  история чатов, лиды               │
        └──(синк)────────┴──────────▲─────────────────────────┘
                                    │
Telegram-бот (long poll) ─┐         │
VK-бот (long poll) ───────┼── задачи в очередь ──→ AI-воркеры
PWA / чат (FastAPI) ──────┘                            │
                                                       ▼
                                        AI-провайдер: основная модель
                                        (планы) + лёгкие (анализ, чат)
                                        + резервный фолбэк
```

Принципы:

- **Один бэкенд-источник правды** — PostgreSQL. Боты, PWA и воркеры не
  держат своё состояние: FSM ботов живёт в памяти (перезапуск = сброс
  диалога, это осознанный компромисс), но все данные — в БД.
- **Очередь вместо вебхуков.** Боты и веб ставят задачи в таблицу
  `job_queue` с приоритетом; отдельные воркеры обрабатывают их. AI-вызовы
  (10–60 секунд) не блокируют хендлеры ботов.
- **Лестница моделей.** Планирование недели — сильная модель; разбор
  тренировки и чат — быстрые; DSL-конвертация и питание — дешёвые. При
  недоступности провайдера — автоматический фолбэк на резервный.

## Сервисы

| Сервис | Что делает |
|---|---|
| Бот Telegram | Long Poll, хендлеры команд, FSM-анкеты, inline-кнопки |
| Бот VK | Bots Long Poll сообщества, паритет фич с Telegram (свой модуль клавиатур: inline-клавиатуры VK режутся на 10 кнопок) |
| Воркеры AI (×2) | Очередь `job_queue`: приоритеты — чат > анализ > доп-задачи > изменения плана |
| Планировщик | Раз в минуту: чьи `review_time_utc` наступили — тому утренняя задача. Дедупликация: одна задача на атлета, а не на чат |
| API (FastAPI) | PWA-эндпоинты (план сегодня/неделя, чат), OAuth intervals.icu, мини-приложение входа из ботов; запускается за nginx |

## Потоки данных

1. **Синк** — по расписанию и «быстрый синк» перед карточками/анализом:
   активности (темп, пульс, каденс, TSS) и wellness (сон, HRV, вес, шаги)
   из intervals.icu в БД. Гостевые аккаунты (без ICU) пропускаются
   guard-ом по префиксу ID.
2. **Утро** — планировщик ставит задачу `morning_greeting` в индивидуальное
   время атлета → воркер: синк → план на сегодня → разбор вчерашней
   тренировки (сравнение **по дате**, не по порядку) → погода → AI-совет →
   детерминированный «ТОЧНЫЙ ПЛАН НА СЕГОДНЯ» с DSL для часов.
3. **План недели** — задача `weekly_plan` → 3 стадии генерации → кнопка
   «Добавить в intervals.icu» → выгрузка событий календаря DSL-ом.
4. **Анализ** — синк → последняя пробежка → круги ICU → расчёт по отрезкам
   (каждый этап сравнивается с таргетом) → вердикт → оценка атлета.
5. **Веб-вход** — кнопка в боте → мини-приложение → OAuth intervals.icu →
   одноразовый state → связка аккаунта, перенос данных гостя на новый ID.

## Схема БД (схема `coach`, ~22 таблицы)

- **Атлеты:** пользователи TG/VK (время утра, локация), профиль (рост,
  дата рождения, анкета, оценка тренера), цели (забег: дата + дистанция),
  пульсовые зоны (7 зон; источники: ICU / анкета / полевой тест / лаборатория).
- **Факт:** активности (ai_analysis JSONB — вердикты прошлых разборов),
  wellness, обувь.
- **Планы:** план недели как JSON (дни monday..sunday + extras
  `<day>_stretch/_indoor` с DSL-комплексами), аудит изменений,
  `pending_actions` — заявки на изменение плана, ожидающие «✅» атлета.
- **AI:** планы питания (КБЖУ, режим), лог промптов (для отладки), очередь
  задач, дневник еды, лабораторные тесты.
- **Чаты/PWA:** история диалогов с rolling-summary, лента PWA, OAuth-сессии,
  лиды (все пишущие ботам).

## Отказоустойчивость и честность

- **Код-гейты вместо «конвенций в промпте»**: инварианты (сумма дистанций,
  зоны, запрет самовольной перезаписи плана) проверяются кодом после
  каждого шага генерации — см. [планирование](features/planning.md).
- **Толерантный JSON-парс** всех ответов AI: валидация + повтор парса с
  правкой хвостов, NULL-safe доступ — модель не может уронить пайплайн.
- **Контроль баланса AI-провайдера**: при низком остатке — алерт админам
  не чаще раза в сутки (инцидент: нулевой баланс молча ломал все планы).
- **Смоук-тесты на каждый шов**: протоколы «бот ↔ воркер» проверяются
  с обеих сторон — односторонний смоук однажды пропустил неработающую
  кнопку подтверждения (смоук был зелёным, кнопка не работала).

## Смежные модули

- `formatters.py` — форматирование планов/дней, единое для TG и VK.
- `weather_service.py` — прогноз погоды (Open-Meteo) + геолокация.
- `lead_capture.py` — middleware, фиксирующая всех пишущих ботам.
- `stats_card.py` / `progress_card.py` — карточки (см. [карточки](features/cards.md)).
- `plan_push.py` — выгрузка плана в ICU (см. [icu-sync](features/icu-sync.md)).
